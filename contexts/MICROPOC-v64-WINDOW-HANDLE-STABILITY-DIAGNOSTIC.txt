RumiAI Computer Control micro-PoC v64
WINDOW HANDLE STABILITY DIAGNOSTIC

STATUS
VALIDATED / REBOUND CONFIRMED PHYSICALLY ON macOS

PURPOSE
Determine whether macOS agent-ctrl window ids such as `pid:<pid>:window:<n>` are stable window identities or observation-scoped positional handles that can rebind when AX window ordering changes.

WHY THIS EXISTS
v62 and v63 physically focused the requested TextEdit document successfully, but immediately afterwards the same target id was reported with the title of the previously pinned document. That was initially classified as stale title metadata. Upstream source inspection showed a stronger explanation: macOS agent-ctrl stores an `AxPinnedWindow { pid, index }`, enumerates the application's AXWindows array by index, and derives window ids from that pid/index pair. Therefore an id can denote a different concrete AX window if the array order changes.

UPSTREAM SOURCE FINDING
agent-ctrl commit inspected: 7cc6b3d6d25ae6064aa1cf56d32df3af6e24a212
File: crates/surface-ax/src/macos.rs
Observed implementation facts:
- AxPinnedWindow contains pid + index.
- list_windows() iterates AXWindows by array index and builds each WindowInfo id from that pid/index pin.
- focus_window(id) parses the id back to pid/index and raises the window currently at that index.

PHYSICAL DIAGNOSTIC RESULT
PASS. Handle rebinding was reproduced directly with two TextEdit windows.

Before focus:
- `pid:60184:window:0` -> rumiai-v64-window-handle-B.txt
- `pid:60184:window:1` -> rumiai-v64-window-handle-A.txt

The observed target was A at `window:1`.

After focusing A:
- `pid:60184:window:0` -> rumiai-v64-window-handle-A.txt
- `pid:60184:window:1` -> rumiai-v64-window-handle-B.txt

Therefore:
- same-id-still-same-window=false
- same-window-still-same-id=false
- window-handle-stability=REBOUND
- independent-focus-verification=PASS
- diagnostic-complete=PASS
- diagnostic_exit=0

CONCLUSION
The macOS agent-ctrl id is NOT a durable window identity. It is an ephemeral action handle derived from the current AXWindows positional index.

ARCHITECTURAL CONSEQUENCE
RumiAI must not describe this id as stable and must not execute a delayed action from id alone.
A previously observed action target must carry enough observation metadata to prove that the current handle binding still denotes the same observed window immediately before action.
If the binding no longer matches, the operation must fail closed with a stale/rebound-handle error rather than act on whichever window currently occupies that index.

The current v62/v63 physical PASS remains valid as evidence that focus delivery works. v64 changes the interpretation of the id contract: the focus implementation is physically functional, but id-only delayed targeting is not sufficiently safe for the general contract.

NEXT MICRO-POC
v65 must introduce a window-handle rebinding guard before any new minimize/maximize/restore/move/resize work.
The guard must preserve the full observed window descriptor needed for freshness validation and fail closed on mismatch before action delivery.

NON-GOALS

- No retroactive alteration of v62/v63 evidence.
- No claim about Windows/UIA id stability.
