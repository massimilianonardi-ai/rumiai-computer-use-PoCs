RumiAI Computer Control micro-PoC v62
VERIFIED WINDOW FOCUS

STATUS
VALIDATED

PURPOSE
Activate Desktop Plugin focusWindow() on macOS using stable window ids from the v60/v61 validated window-list observation, without exposing backend or OS-specific HOW through the public Computer Control facade.

ARCHITECTURAL INVARIANT
RumiAI defines the Desktop Plugin focusWindow(application, window) contract.
The macOS plugin owns HOW a concrete window is focused and HOW the postcondition is verified.
agent-ctrl remains a private backend/tool.
The public Computer Control facade is unchanged in v62.

UPSTREAM BACKEND CONTRACT CONFIRMED
agent-ctrl exposes `focus-window <id>` and documents window-list as the discovery primitive for ids used by focus-window. The focus-window action brings the selected window to the foreground and re-pins the session on it.

VALIDATED IMPLEMENTATION
- Backend agentCtrl.focusWindow(windowId) uses `agent-ctrl focus-window <id> --json`.
- macOS Desktop capability `window.focus` is IMPLEMENTED.
- macOS focusWindow(application, window) requires a stable window id.
- Precondition: validated plugin listWindows(application) proves the id belongs to the resolved application.
- Focus executes through backend agentCtrl.focusWindow(targetId).
- Postcondition observation uses direct backend agentCtrl.listWindows() with no intervening target-process snapshot.
- Success requires the requested id to be present with pinned=true after the action.
- FOCUSED + verified=true is returned only when that postcondition is satisfied.

WHY NO POST-ACTION plugin listWindows()
The validated plugin listWindows(application) intentionally performs a fresh target-process snapshot before enumeration so it can establish the application context. Calling it after focus-window could re-pin a different window and destroy the postcondition. Therefore post-action verification reads the already-pinned session window list directly inside the macOS plugin.

BOUNDARY VALIDATION
PASS. The boundary test proved:
- stable target id requirement;
- target ownership precondition;
- backend focus-window routing remains private;
- no post-action plugin listWindows/application snapshot re-pin;
- target id pinned postcondition;
- public Computer Control facade remains unchanged in v62.

PHYSICAL VALIDATION
PASS on macOS with two real TextEdit windows.

Observed sequence:
- initial pinned window: rumiai-v62-window-focus-B.txt, id pid:59940:window:0;
- target unpinned window: rumiai-v62-window-focus-A.txt, id pid:59940:window:1;
- plugin focus returned FOCUSED, verified=true;
- postcondition reported target id pid:59940:window:1 with pinned=true;
- independent TextEdit front-document observation reported rumiai-v62-window-focus-A.txt;
- physical-window-focus=PASS;
- physical_exit=0.

KNOWN OBSERVATION / DEBT
The immediate post-action backend window-list associated the correctly pinned target id pid:59940:window:1 with the stale/mismatched title rumiai-v62-window-focus-B.txt. Independent physical observation proved the actual front document was rumiai-v62-window-focus-A.txt.

This does not invalidate v62 because the focus contract is id-based and both the id pin transition and independent physical focus passed. Do not treat immediate post-focus title metadata as authoritative until a separate metadata-consistency micro-PoC investigates it.

fixture-cleanup=WARN was test cleanup only and did not affect the functional result.
